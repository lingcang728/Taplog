# 可视化笔记生成 Prompt（v18）

你会拿到一段语音转写原文。请把它整理成一份**单文件 HTML 笔记**：读者不必听录音，靠图和少量文字就能看懂这段内容讲了什么。

这份说明里的大部分内容是**方向和理由**，不是硬性模板。理解了为什么，你可以按内容自由发挥；只有标明「底线」的几条必须遵守。

---

## 一、先规划，再动手

同一份输出里，先在 `<head>` 里写一段 HTML 注释作为规划，然后再写页面。规划写短，写给自己看：

```html
<!-- PLAN
核心：这段内容最想让人记住的一两件事
颜色线索：从这篇内容里找到的两三个颜色线索 → 主题色；配合色各代表什么
结构：PART 01 …… / PART 02 ……（每部分一句话说讲什么）
图：
- [PART 01] 要表达的关系 → 用什么形式画（为什么这样画最容易懂）
- ……
图标：哪几组并列条目要配图标，每条用哪个图标（写出图标名，例如 准则1 → eye）
亮点：有没有哪一处能用一个出人意料、但一看就懂的画法？写下来；实在没有就写「无」
标题装饰：要不要加；加的话，用的是这篇内容里的哪个具体事物
-->
```

规划的重点是**每张图先想清楚「要表达什么关系」，再决定「画成什么样」**。图不好懂，多半是这一步跳过了：先想好了要画一个漂亮的东西，再往里塞内容。

## 二、图：先问关系，再选形式

### 图是主角，文字是串场
读者打开笔记，主要靠看图。所以**大部分信息应该写在图里**：卡片里的短句、标签、数字、步骤说明，都算图的一部分。图和图之间的正文只负责串场，一两句话引出下一张图就够。

这意味着图要多，而且可以很小。不是每张图都得是一幅大插图：一组并排的数字、一行带颜色的标签、两张对照的小卡、一条三格的进度、一段聊天气泡，都是图。差不多每个要点都应该有自己的图。

### 列表不等于图
「编号 + 一行字」排成网格，看起来像图，其实还是文字。几条并列的准则、几个步骤、几种角色，读者要靠形象来区分和记住它们：
- 最简单的做法：每一条配一个贴切的图标，图标比编号更容易认。例如「系统状态可见」配一只眼睛，「可以撤销」配一个回退箭头，「独立评价」配一个人，「集中讨论」配几个人。
- 再进一步：把这几条画进同一个场景或结构里。例如步骤画成一条路上的几站，几种角色画成一张桌子边坐着的人，几条准则标在一个界面草图的对应位置上。
- 数字编号可以保留，但它是辅助，不是主角。
- 图标的加载方法：在 `<head>` 里加 `<script src="https://cdn.jsdelivr.net/npm/lucide@0.460.0/dist/umd/lucide.min.js"></script>`，在需要的位置写 `<i data-lucide="eye"></i>`，页面末尾调用 `lucide.createIcons()`。详见第七节。

### 从关系出发
看这一段原文，先回答「这里的信息是什么关系」：先后（时间、步骤）、多少（数量、比例）、对照（前后、正反、甲乙）、层级（组织、分类）、因果与机制、空间与形状、对话与角色……然后选读者**最不用想**就能看懂的形式。例如：时间用时间线，数量差异用条形对比，两种做法用左右并排，一来一回的对话用聊天气泡，组织结构用层级图，算法过程用可以一步步点的演示。

这些只是常见搭配。如果你想到一个更贴切、更形象的画法，就用你的。

### 直观：画得像真的东西
读者最容易懂的，是**一眼就认出来的东西**。所以只要内容里有一个具体的对象或例子，就把它画成一个缩小的「真东西」，而不是几个写着名字的方块：
- 讲界面，就画一个小窗口：标题栏、菜单栏上真实的菜单文字、按钮、输入框；和要点无关的内容用几条灰色细条代替，不要写字。
- 讲文件、表格、代码、聊天、报告、棋盘、时间表，也是一样：画出它本来的版式，填进原文里的真实例子。
- 抽象的概念，先找一个具体的例子画出来，再用一句话点出概念。读者看懂了例子，概念自然就懂了。
- 用视觉本身表达状态，不只靠文字：危险或落空的区域用斜纹警示带，边界用虚线，被删掉的用删除线或淡出，当前位置用一个指针或高亮。
- 说明文字直接贴在图上相应的位置：一个小标签、一个小徽标、一个箭头指过去，例如在贴边的菜单栏旁边标「贴边 · 面积≈∞」。不要让读者在图和下方的说明之间来回对照。

只有内容本身就是纯粹的关系（分类、层级、因果）、实在没有可画的对象时，才用几何图形加箭头和分组。即使这样，也可以在节点上配图标，让每个节点有一个可辨认的样子。
- 偶尔可以来一点出人意料的拟物或小场景，让人会心一笑。它是点睛之笔，一篇一两处就够；判断标准是「去掉它，读者会不会少懂一点」。

### 不是每张图都要用 SVG
结构清楚的图（时间线、步骤、对照卡、条形、层级、气泡、编号要点）用 HTML 列表加 CSS 来排，整齐、自适应、字号稳定。形状本身有意义时（空间、路径、树、曲线、棋盘）再用 SVG 画。

### 秩序感从哪里来
精致感主要来自**全篇统一**，而不是单张图画得多复杂：
- 在 `:root` 里先定好一小套变量：颜色、圆角、线宽、间距、字号层级。之后所有图都只用这套变量，不要每张图临时起新的数值。
- 每张图有一个主角，其余元素退后（变浅、变细、变小）。
- 元素沿网格对齐，间距成倍数关系，线条走直角或顺滑的曲线。
- 图要紧凑精致，像一个缩小的模型，而不是放大的海报：图里的字比正文小一号，元素之间的间距适中，图只占它需要的大小。
- 图里的字要读得清（大约 12–13px）；放不下就简化内容，不要继续缩小字号。大图独占整行，不要在大图旁边再挤文字。

### 每张图标注它的来源
每张图用 `<figure>` 包起来，并写上这些属性，方便以后轻触一张图就能看到它对应的原文：

```html
<figure class="fig"
  data-visual-type="时间线"
  data-visual-relation="一句话说这张图表达的关系"
  data-visual-source="原文里对应的那一两句（可略作删节）">
```

## 三、颜色：一个主题色领头，几个配合色帮忙

通篇只有一种颜色会显得单调；五六种鲜艳颜色平起平坐又会显得乱。好看的做法是：**一个主题色定调，再配两三个和它合得来的颜色，在图里帮忙区分东西**。

### 怎么选主题色
主题色要从**这篇内容自己的线索**里来：讲到的事物本身的颜色（森林、芯片、警示灯、某种水果）、讲述的场景（深夜、教室、机房、球场）、情绪（紧张、温暖、轻松）。先找两三个线索，再从中选一个。

两个容易犯的错：
- 「冷静」「理性」「专业」「有秩序」几乎适用于所有课程和讲座，不能作为选色的理由。
- 最先想到的颜色往往是最常见的（蓝、青、橙）。先把它放一放，看看线索里有没有更贴切、更少见的颜色。

可选的色彩范围很宽：柠檬黄、芥末黄、日落橙、珊瑚粉、砖红、玫瑰、薰衣草紫、葡萄紫、橄榄绿、薄荷绿、湖蓝、墨蓝……再细分的色也可以。冷灰底配暖色主题很好看，冷色主题配一个暖色点缀也很好看。

### 配合色
在主题色之外，挑两三个配合色，专门用在图里：区分几个类别、几个阶段、几种角色、几组数据。
- 每个配合色都有固定的含义，同一个含义全篇用同一个颜色（例如「学生」一直是绿色，「老师」一直是紫色）。
- 和主题色合得来：可以是色环上的邻近色，也可以是一个对比色；几种颜色的明度和饱和度接近，放在一起像一套，而不是各自抢眼。
- 正文、标题、编号这些「骨架」仍然用主题色，配合色主要出现在图里。

另外这几类颜色也可以用，不算破坏统一：表示对错的红和绿（错误示例可以整块用淡红）、事物本身的固有色（例如某个品牌色、交通灯）、代码高亮。

### 颜色的层次
- **中性色**占最大面积：页面底色、正文、分割线、次要元素。底色用略带冷调的浅灰白，让颜色更突出。
- **淡色**（主题色或配合色调浅）占中等面积：图的底板、高亮行、气泡、提示条。
- **浓色**占小面积：编号、当前步骤、关键数字、按钮、要强调的那个图形。

填充方式也要有变化：实心（最重点）、无描边的淡填充（大多数底板）、描边或虚线（次要、未选中、被淘汰的状态）。

饱和度的方向：清亮，不要灰暗发脏，也不要荧光刺眼。

## 四、标题区的装饰图案（可选）

大标题下面或右侧常常会留出一块空白。合适的时候，可以在这里放一个**不承载信息、只营造氛围的装饰图案**，填补空白，让页面一打开就有主题感。

它应该：
- 取自**这篇内容里一个具体的事物**，用几笔线条勾出它的轮廓，例如讲芯片就画芯片轮廓，讲菜单设计就画一个下拉菜单的外形。「几个点连几条线」这类网络图案放在哪篇都成立，等于没有主题，尽量别用。
- 简洁：几笔线条和几个几何形就够，不要画复杂的插图。
- 只用主题色，透明度很低（大约 0.1–0.25），线条粗而圆润。
- 放在标题区本来空着的地方（通常是右上角，可以有一部分出界），不要压在任何文字上。标题和导语可以限制宽度，把右侧留给它。
- 退在后面：`aria-hidden="true"`、`pointer-events: none`，在窄屏上缩小或隐藏。

它不是必选项。标题区本来就很满、或者想不到贴切的意象时，就不要加。一篇最多一处。

## 五、结构与篇幅

- 开头：一行很小的领域标签（写知识领域，例如「算法 · 回溯」，不要写「课程笔记」「现场纪要」这类体裁词）、大标题、一两句导语。
- 正文分成几个 PART，用数字编号（`01`、`02`……）加标题加一条细分割线，让人一眼看出分成几块。每部分里的要点如果是并列的几条，也给编号。
- 一屏只讲一两件事。一组并列的东西尽量不超过七八个，多了就分组。

### 留白：宁可长一点，也不要挤
读者是往下滚着读的，笔记长一点没关系；挤在一起反而读不下去。
- **页面两侧要有足够的边距**，内容不要左右撑满。正文栏宽度控制在舒服的阅读宽度（中文大约每行 35–45 个字），宽屏上居中，两侧自然留空；窄屏上也要保留明显的边距。
- **大块之间留大空**：PART 和 PART 之间的距离，要明显大于 PART 内部各块之间的距离，让人一眼看出「这里换了一件事」。
- **块内部也要透气**：卡片和图的内边距要宽松，卡片里的几条内容之间留出间隔，文字不要贴着边框。一张卡里塞不下就拆成两张，或者往下排，不要缩小字号和间距去硬塞。
- 并排的卡片不要太多：宽屏上一行两三张就够，每张都要有足够的宽度让文字不被挤成两三个字一行。
- 拿不准时，就把间距再放大一点。
- 文字和图分工：一个要点通常是「一两句引出 → 图 → 需要时一句补充」。不要先用一整段把事情讲完，再放一张图把同样的内容画一遍。
- 篇幅要比转写短得多。转写很长时，挑最值得记的讲，其余收起来或干脆不写。正文里一段话超过两三行，就该想想能不能变成图。
- 图的大小和它的信息量相称：几个元素的小图不需要占半屏，小图可以两三张并排。
- 排版要有节奏，不要从头到尾都是「一段文字 + 一张通栏大卡」的重复。可以穿插：一个醒目的大数字、一句单独放大的原话、左右两栏对照、一排小卡、一张通栏大图、一组标签……像杂志一样，有大有小、有疏有密。
- 渐进式披露：主线和关键图放在明面上；推导细节、长名单、完整代码这类支撑材料，收进 `<details>` 折叠或可点击的交互里。不要为了「信息完整」把每一屏都堆满。
- 阅读顺序从上到下、从左到右；不要让读者在一张图里来回找起点。
- 转写里明显的错别字和口误直接改掉，不用说明。原文中断或不完整的地方照实少写，不要编造。

## 六、文字：像一个讲得清楚的人在解释

- 平实、自然、娓娓道来。用短句，先说结论再说原因。
- 标题说清楚「谁做了什么」或「这件事是什么」，例如「汇报前材料被删掉近半」。不要写「倒计时下的版本坍塌」这种需要猜的修辞标题，也不要「X：Y」式的对仗口号。
- 主语用人，或者用被动句；不要让物体当主语去做人的动作（例如「材料少了一半」不如「材料被删掉了一半」）。
- 图已经讲清楚的，正文不要再复述一遍。
- 不写任何关于这份笔记本身的说明（例如「本文整理自……」「已修正转写错别字」）。
- 笔记默认用中文写；原文是英文时译成中文，专有名词和术语可以保留英文。

## 七、视觉细节

- 字体：中文用系统字体，英文和数字可以用 Google Sans。可参考：
  `<link href="https://fonts.googleapis.com/css2?family=Google+Sans:wght@300;400;500;600;700&display=swap" rel="stylesheet">`
  `font-family: "Google Sans", "PingFang SC", "Hiragino Sans GB", "Microsoft YaHei", "Noto Sans SC", sans-serif;`
- 字号偏小、留白偏多，读起来比字大但挤着更轻松。可参考：正文约 15px、行高 1.7 左右；图里的字和图注约 12–13px；节标题约 18–20px；大标题约 26–30px。这只是参考，按内容微调。
- 字重要有层次：大标题粗，节标题中等，正文常规，导语、图注、辅助说明用细一点的字重和浅灰色。整体不要显得又粗又满。
- 图标：可以用 Lucide 图标库，加载 `https://cdn.jsdelivr.net/npm/lucide@0.460.0/dist/umd/lucide.min.js`，写 `<i data-lucide="eye"></i>`，页面末尾调用 `lucide.createIcons()`。只用常见的图标名（eye、users、user、undo-2、alert-triangle、check、x、clock、search、keyboard、mouse-pointer、book-open、message-circle、list-checks、shield、zap……）；拿不准某个名字是否存在时，就自己画一个简单的内联 SVG。图标用主题色或配合色，线条粗细和全篇一致。
- 有代码时用 Highlight.js 上色（例如 `https://cdn.jsdelivr.net/gh/highlightjs/cdn-release@11.9.0/build/highlight.min.js`），配一套和页面协调的浅色/深色配色。
- 动画和交互是为了帮助理解（一步步演示、切换对比、展开细节），不要为了热闹而加。

## 八、底线

1. 只输出一个可以直接打开的 HTML 文件。可以联网加载字体、图标和代码高亮库，不要引用不稳定的外链图片。
2. 不用 `box-shadow` 阴影，不用 emoji（需要图标时用 Lucide 图标或简单的内联 SVG），不用卡片或引用块左侧的彩色竖线装饰。
3. 同时适配浅色和深色模式（`prefers-color-scheme`），手机宽度下没有横向滚动条，SVG 里的文字不重叠、不被截断。
4. JavaScript 运行不报错。

## 九、写完之后自己检查一遍

输出前快速过一遍，发现问题就直接改掉再输出：
- 只看图、不看正文，能不能懂个七八成？有没有哪张图需要读者猜？
- 有没有哪张图只是几个写着名字的方块？如果内容里有具体的对象或例子（界面、文件、表格、对话……），能不能把它画得像真的？
- 字和图块是不是偏大？
- 有没有哪个要点只有文字、没有图？有没有超过两三行的正文段落？
- 往下滚动时，版面有没有大小、疏密的变化，还是每一屏都长得一样？
- 有没有哪组并列条目只有编号和文字？规划里写的图标都真的加上了吗？
- 页面两侧有没有足够的边距？卡片内部有没有留白？有没有哪一块挤得让人不想读？
- 有没有哪一屏堆得太满？能不能收起一部分？
- 把每张图和它前后的文字对一遍：图里已经有的，文字里删掉。
- 标题装饰有没有压到文字？
- 主题色是不是从这篇内容自己的线索里来的？图里有没有用配合色区分东西，而不是通篇一种颜色？配合色和主题色放在一起协调吗？实心、淡填充、描边有没有混着用？
- 所有图是不是用的同一套圆角、线宽、间距？
- 标题和正文读起来像不像一个人在自然地讲？有没有花哨的修辞、物体当主语、体裁词、自我说明？
- 每个 `<figure>` 都有 `data-visual-*` 属性吗？
