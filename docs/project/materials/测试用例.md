## 一、两个版本给的片段有什么不同

| | 版本一（C1）：单点溯源 | 版本二（C2）：全部片段 + 关系标签 |
|---|---|---|
| 每条要点下面 | 只有 1 个时间点：这条结论**第一次**出现的地方 | 这条要点相关的**所有**片段，每段标关系：出处 / 复述 / 补条件 / 纠正 / 解释 / 举例 |
| 点开以后 | 从该时间点开始播放，用户可以自己往后拖 | 只播这一段；如果后面还有补充，播完会提示 |

两个版本的要点文字**完全一样**，只有片段部分不同。

关系标签的意思（界面上用英文）：

| 中文 | 界面英文 | 意思 |
|---|---|---|
| 出处 | Source | 结论第一次出现 |
| 复述 | Restated | 后面又说了一遍，意思没变 |
| 补条件 | Condition | 补充了适用条件或限制 |
| 纠正 | Correction | 推翻或改口 |
| 解释 | Explanation | 说明原因 |
| 举例 | Example | 举例子或演示 |

### 2.2 测试题（做题顺序：T2 → T3 → T1）

T2 必须最先做：T1 的答案里包含 T2 的答案，先做 T1 会泄题。

**T2 陷阱题**
- 题目：“判断讲者是否支持下面这个说法：**一个自建数据库的小团队只有两台服务器，也应该直接用 TiDB 替换 MySQL 主从。**”
- 第一步：只看笔记，不许播放原声。选“支持 / 不支持 / 笔记里看不出”，并打信心分 1–5。
- 第二步：可以播放原声。重新选，重新打信心分。
- 标准答案：**不支持**。依据是 L01-K1-S7（29:59）：两台机器没法部署，生产环境至少三台。
- 陷阱在哪：笔记和 S1、S2 都只说“能用就用”“自建就用分布式”。只听单点溯源的人容易更自信地答“支持”。
- 记录：两步的答案和信心分，第二步播放了哪些片段。

**T3 找原话题**
- 题目：“找到讲者说‘换成 TiDB 后有些查询会变慢’的那句话，写下时间点。”
- 标准答案：28:43–29:13（L01-K1-S5）。时间点在这个范围内 ±15 秒都算对。
- 记录：用时、对错、播放次数。

**T1 适用条件题**
- 题目：“笔记里说多点的策略是‘能用 TiDB 就不再用 MySQL’。讲者提到了哪些不适合迁到 TiDB 的情况？尽量列全。”
- 标准答案（共 4 条）：
  1. 下游工具强依赖 binlog（S4）
  2. 对延迟敏感，有些 SQL 会变慢（S5）
  3. 用了存储过程、触发器或自定义函数（S6）
  4. 只有两台机器，生产环境至少要三台（S7）
- 评分：答对几条记几分（0–4）。主要指标是“至少答对 1 条”的比例。
- 记录：用时、得分、播放了哪些片段。

## 三、L02《基于 eBPF 的云原生可观测性深度实践》（A 类，38:46）

### 3.1 结论 → 远处补充

**要点 K1：AutoTracing 不用改任何代码、不用插桩，就能做完整的分布式追踪。**

| 片段 | 时间 | 关系 | 字幕原话（节选） |
|---|---|---|---|
| S1 | 02:08–02:19 | 出处 | “auto [tracing]，那不用去做任何的插码插桩，就能够去实现分布式的追踪” |
| S2 | 09:00–11:06 | 举例 | Istio 演示：“没有做任何代码的改造，没有做任何的插桩……这确实是零插桩的” |
| S3 | 14:02–14:30 | 补条件 | “它不像 java agent 获取到的这个 [span] 那样……进程里面还有很多很多的函数……这是一个代价的问题……只会去将锚点挂在 request 上面” |
| S4 | 16:31–17:00 | 补条件 | “并不是所有的这些语言都是使用的这个 kernel threading model……go 是协程化的……和 eBPF 识别到的 thread id 可能没有太大的关系” |
| S5 | 23:03–25:02 | 解释 | 协程问题的解决办法：跟踪 goroutine 的创建，把相关协程“染成同一个颜色” |
| S6 | 25:27–27:02 | 补条件 | “我们发现了迄今为止还没有去解决的一个问题……跨线程的，通过队列的方式……比如 redis、kafka……在一些场景下有现成的 id”（网关的 X-Request-ID 能解决一部分） |
| S7 | 31:06–32:15 | 补条件 | “对于一个进程的内部，我们不希望用 eBPF 这种特别底层的方式去抓函数之间的调用，虽然它是可行的，但是它的开销会比较大……[eBPF] 在进程内部以及有一些跨线程的场景下，我们不能去做到……两种追踪的方式结合起来” |
| S8 | 34:31–35:02 | 解释 | 和 OTel 插桩结合以后，异步、队列、跨线程的地方“也不会断掉” |
| S9 | 38:01–38:10 | 复述 | 未来工作：“怎么来去解决跨线程的问题” |

间隔：从 S1 算起，S3 隔 11.9 分钟，S4 隔 14.4 分钟，S6 隔 23.3 分钟，S7 隔 29.0 分钟。

注意：S1 后面紧跟着（02:19）就有一句“我们怎么将二者结合起来”，是在预告讲座的目录。单点溯源的人从 02:08 往后听，可能会听到这句。所以版本一的时间点要定在 S1 的 02:08，不能往后挪，报告里也要如实写这一点。

### 3.2 测试题（做题顺序：T2 → T3 → T1）

**T2 陷阱题**
- 题目：“判断讲者是否支持下面这个说法：**只靠 eBPF AutoTracing、不做任何插桩，请求经过 Kafka 这类消息队列在线程之间异步传递时，也能自动把整条链路串起来。**”
- 两步做法同 L01-T2。
- 标准答案：**不支持**。依据是 S6（25:27）“迄今为止还没有去解决”，以及 S7（32:09）“跨线程的场景下我们不能去做到”。要和 OTel 插桩结合才不会断（S8）。
- 陷阱在哪：S1、S2 都说“零插桩”“全都追踪下来了”。

**T3 找原话题**
- 题目：“讲者解释过为什么不用 eBPF 去抓进程内部的函数调用。找到这句话，写下时间点。”
- 标准答案：31:06–31:30（S7，“开销会比较大”）。14:02–14:30（S3，“这是一个代价的问题”）也算对。允许 ±15 秒。

**T1 适用条件题**
- 题目：“笔记里说 AutoTracing ‘不用改代码就能做完整的分布式追踪’。讲者后来说了哪些它做不到或做不完整的地方？”
- 标准答案（2 条主要的，1 条加分）：
  1. 进程内部的函数级调用不抓：开销大，要靠 Java agent 或 OTel 补（S3、S7）
  2. 通过队列跨线程的异步调用还没解决（S6、S7）
  3. 加分：协程语言（如 Go）要额外处理，讲者说已经解决了（S4、S5）
- 评分：主要的 2 条，答对几条记几分（0–2）；第 3 条单独记，不计入主指标。

## 四、L03《LLVM 编译器后端常见优化手段》（B 类对照，39:33）

### 4.1 通读结论

全文没有发现隔 5 分钟以上的补充或改口。讲者的限制条件都是当场就说的，例如：
- 15:01：DAG 指令选择只能在基本块内做，离介绍 DAG（14:00）约 1 分钟。
- 29:31：指令调度例子里，第一步“选得很草率”，随即给出更优做法，离例子开始（27:01）约 2.5 分钟。
- 31:32：“当前算法下最优，全局不一定最优”，当场说明。

**一处边界情况，出题时避开：** 03:03 讲者说“LLVM IR 把前端和后端完全解耦”是最大的优势；33:01–35:00 又说中端拿不到指令延迟、寄存器压力这些硬件信息，向量化只能靠估算。这是解耦带来的代价，但讲者没有把它当作对前面说法的修正，所以不算远距离补充，也不要拿它出题。

### 4.2 对照题

每位被试做 2 道对照题，两个版本各 1 道：T4a 配版本一，T4b 配版本二，在被试之间轮换。

**T4a**
- 笔记要点：“开优化时，LLVM 主要用贪婪（Greedy）寄存器分配。”
- 片段：S1 21:30–22:31 出处；S2 22:31–23:02 解释。
- 题目：“LLVM 为什么不用 PBQP 做寄存器分配？”
- 标准答案：PBQP 想用更数学的方法解，但没解决编译时间太长的问题，现在基本没人维护（22:31–23:02）。

**T4b**
- 笔记要点：“Fast 指令选择是 O0 时的默认方案，选得很快。”
- 片段：S1 13:00–13:30 出处；S2 13:30–14:00 解释。
- 题目：“Fast 指令选择为什么快？”
- 标准答案：它几乎不看指令的上下文，只看当前这一条，能选就马上选，也不做优化（13:30–14:00）。

看什么：两个版本在对照题上的用时和正确率应该差不多。如果版本二明显更慢，说明多出来的片段和标签增加了负担（对应 RQ 里的负担问题）。
